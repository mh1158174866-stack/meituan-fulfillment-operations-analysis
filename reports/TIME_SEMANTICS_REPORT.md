# 时间与业务语义审计

本报告由 `scripts/audit_time_semantics.py` 全量只读生成。Unix 秒统一在 DuckDB 会话中按 `Asia/Shanghai` 解释；不展示单条记录、原始 ID、坐标或行为序列。

## 1. `dt` 是运营归属日

- `dt` 覆盖 2022-10-17 至 2022-10-24；按 Asia/Shanghai 解释的平台下单本地日覆盖 2022-10-11 至 2022-10-24。
- 同一订单跨多个 waybill 时，`dt`、`is_prebook`、`platform_order_time` 不一致的订单为 61 个。
- 因预订单可提前下单，`dt` 不应机械地替换为 `platform_order_time` 的自然日；后续经营统计应以 `dt` 作为运营归属日。

## 3. `wave_start_time` 索引问题

- wave 表共 206,748 行；`wave_start_time` 最小值 1,665,936,060、最大值 1,666,628,609、去重值 158,483 个。
- 其中落在 0 至 206,747 的值有 0 行，落在常见 Unix 秒范围的值有 206,748 行，因此它不是行号型索引。
- 通过波次订单集合连接已接受 waybill，可重构 206,748 个波次的最早接受时间；原 `wave_start_time` 与重构值相等 140,844 行，不相等 65,904 行。
- 在不相等及全部波次中，原值早于最早接受时间 0 行、晚于最早接受时间 65,904 行；差值范围为 0 至 15,692 秒。
- 原值与波次最早派单时间相等 0 行，与 `order_ids` 首个列表成员的接受时间相等 131,792 行，与波次内任一成员接受时间相等 206,748 行。
- `wave_end_time` 落在常见 Unix 秒范围的有 206,748 行，与波次内最大送达时间相等 206,748 行。
- 结论：`wave_start_time` 是合法 Unix 秒，但与官方“波次首单接受时间”定义存在索引/对齐问题，不能直接用于持续时长。若第二阶段需要波次开始时间，应以波次成员中已接受订单的最早 `grab_time` 重构并保留审计来源。

## 4. `dispatch_time` 是 checkpoint 语义

- 两张 dispatch 表各包含 24 和 24 个 `(dt, dispatch_time)` checkpoint，共有 checkpoint 为 24 个，覆盖 8 个 `dt`。
- 按 Asia/Shanghai 解释，checkpoint 时间范围为 2022-10-17 11:25:14+08:00 至 2022-10-24 11:30:17+08:00。
- 每个 checkpoint 的待分配订单行数范围为 591–733；候选骑手行数范围为 2,482–2,680。
- dispatch_waybill 共 15,921 行，其中 checkpoint 时间与该订单最终已接受 waybill 的 `dispatch_time` 相等 1 行（0.006281%）。
- 两张 dispatch 表是 24 个选定派单时点的输入快照，用于还原当时订单集合和候选骑手集合；不是覆盖全周期的逐事件派单日志。

## 5. 阶段 D 结论

- 后续按 `dt` 归属运营日，Unix 秒按 Asia/Shanghai 转换。
- 预订单提前下单和跨自然日现象已在订单粒度量化，不应被误判为日期脏数据。
- 顺序异常与已接单未完成记录已单独量化，原始记录不做静默修正。
- `wave_start_time` 和 dispatch checkpoint 的语义限制已明确；本阶段不构建正式事实表。
