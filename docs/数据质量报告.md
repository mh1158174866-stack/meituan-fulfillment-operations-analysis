## 3. 字段、类型、缺失与重复

- 四张表均无空值、无完全重复行。
- 全运单表：654,343 个唯一运单 ID，568,546 个唯一订单 ID，4,955 个唯一骑手 ID。
- 57,770 个订单存在多个运单，单订单最多 17 个运单，符合拒单后重新生成运单的业务定义。
- 85,797 条拒绝运单的 `grab_time`、`fetch_time`、`arrive_time`、`grab_lat`、`grab_lng` 均为 0，与官方补充说明完全一致。
- 568,546 条接受运单中有 1 条 `arrive_time=0`，因此完成运单为 568,545 条；后续配送时长与波次关联均使用完成运单。
- 波次表 `(dt, courier_id, wave_id)` 复合主键无重复，共 206,748 个波次。
- 派单订单表 `(dt, dispatch_time, order_id)` 与候选骑手表 `(dt, dispatch_time, courier_id)` 均无重复。

## 4. 业务时间与 `dt` 差异

- 原始 `dt` 范围：2022-10-17 至 2022-10-24。
- `platform_order_time` 按 UTC 取日期时，627,740/654,343 条与 `dt` 一致（95.93%）。
- 按 Asia/Shanghai 取日期时，652,485/654,343 条一致（99.72%），不一致 1,858 条。
- 不一致记录中预订单 1,704 条、非预订单 154 条；预订单日期一致率为 92.93%，非预订单为 99.98%。
- `dt - business_date_cn` 的偏移为 0—7 天，其中偏移 1 天 1,753 条，说明主要差异来自提前下单，不能简单把 `dt` 当作下单日期。
- 派单订单/候选骑手表的 `dispatch_time` 在 UTC 与 Asia/Shanghai 下均与 `dt` 100% 同日。

项目主分析将保留三个字段：原始 `dt`、UTC 事件时间和 Asia/Shanghai 业务时间。需求分析使用 `platform_order_time` 的 Asia/Shanghai 日期；参考报告复核单独使用其 UTC 口径，避免混用。

## 5. 主键与表关联覆盖率

- 派单订单表的 15,921 个 `(dt, order_id)` 全部在全运单表中找到，覆盖率 100%。
- 派单订单与候选骑手各有 24 个 `(dt, dispatch_time)` 检查点，双向覆盖率均为 100%。
- 波次 `order_ids` 共解析出 568,545 个订单引用，全部在全运单表中找到，覆盖率 100%。
- 波次引用数恰好等于完成运单数，为订单/波次关联提供了额外交叉验证。

关联关系不是简单四表一对一：全运单为运单粒度，一个订单可多次生成运单；派单输入按检查点组织，候选骑手与待派订单在检查点内是多对多候选集合；波次以 `(dt, courier_id, wave_id)` 唯一标识并包含订单集合。

## 6. 事件顺序与异常值

- 在两端时间戳均非 0 时，下单→推单→派单→接单→取餐→送达各相邻节点均无逆序。
- 官方说明 `estimate_meal_prepare_time` 是“预计餐备妥时间”，不是硬约束，因此不把取餐早于该时间判为事件顺序错误。
- 206,748 个可核对波次中，65,904 个原始 `wave_start_time` 与波次内最早 `grab_time` 不一致，占 31.88%；不一致波次平均绝对误差 312.09 秒，最大 15,692 秒。
- 所有波次的 `wave_end_time` 都与波次内最晚 `arrive_time` 一致。

因此后续 DWD 层将重建 `wave_start_time_corrected=min(grab_time)`，保留原值和差异标记，不直接覆盖源字段。

## 8. 第一阶段结论

第一阶段通过，保留一项未决口径：专区/多区域骑手分组不纳入已验证 KPI。官方数据、质量、时间、关联、核心 KPI 和高峰方向均已复核，满足进入 DWD 清洗与核心经营分析的条件。

## 9. 第二阶段轻量分析数据验收

第二阶段将官方 CSV 作为只读 ODS 输入，在本地 DuckDB 中持久化 7 个核心对象：

| 对象 | 实际行数 | 结构/关联验收 |
|---|---:|---|
| `dwd_waybill` | 654,343 | `waybill_id` 唯一；与原表行数一致 |
| `dwd_order_wave_bridge` | 568,545 | 复合键唯一；完成运单关联孤儿键为 0 |
| `dwd_courier_wave` | 206,748 | 复合主键唯一；每个波次均成功重建起点 |
| `ads_operations_overview` | 13 | 按 Asia/Shanghai 平台下单日聚合；订单总数回勾 568,546 |
| `ads_hourly_supply_demand` | 223 | 小时订单总数回勾 568,546；容量公式逐行复算一致 |
| `dws_courier_efficiency` | 4,955 | 骑手数与阶段一一致 |
| `ads_anomaly_diagnosis` | 11 | 仅保留异常类型的聚合分子、分母、比例和阈值 |

运单状态回勾为 85,797 条拒绝、568,545 条完成和 1 条已接受未完成，合计 654,343。订单—波次桥的 568,545 条引用全部能关联到同日、同骑手的完成运单。修正后 65,904 个波次起点与原值不同，波次终点差异仍为 0；177,825 个同日连续波次间隔非负，未发现波次重叠间隔。

口径复算结果：

- 运单加权接单率 86.8881%，骑手等权接单率 84.7436%；
- 完成运单加权平均配送时长 25.72 分钟，骑手等权平均为 27.10 分钟；
- 完成运单平均全链路时长 35.49 分钟；
- 完成运单超时率 15.0081%，分子 85,328，分母 568,545；
- 修正波次平均时长 37.18 分钟，平均负载 2.75 单；
- 修正起点后的非负空闲时长均值 43.11 分钟；`<=240` 分钟的条件复核口径为 26.08 分钟。

以上只是指标口径和工程回勾，不构成阶段三的分时、分组业务结论。

## 10. 确定性与隐私验收

`scripts/run_stage2.sh` 对同一官方输入就地重建两次。首次并行聚合暴露出浮点归并顺序会使三张聚合表的语义哈希不稳定；构建脚本改为单线程聚合后，7 张表的结构、行数和全表语义哈希均完全一致。指纹 JSON 只包含表结构、行数和哈希，不包含原始值或 ID。

隐私扫描检查 40 个 Git 候选文件并通过：官方 CSV、ZIP、PDF 数据附件、本地 DuckDB、指纹 JSON 和所有明细级中间数据均不对 Git 可见。人工复核确认新增公开文件只包含字段名、公式、规模和聚合统计。

## 11. 第二阶段结论

通过。7 个轻量核心对象的粒度、主键、关联、时间、状态、公式和有效样本量均已固定，一键重建、双重确定性校验和隐私扫描通过。专区/多区域分组仍因不可审计而不纳入；小时容量只作为离线代理。
